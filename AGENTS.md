# Repository Guidelines

## Project Structure & Module Organization

Eggy is a Zig 0.17 game engine that games use as a package: they `zig fetch` it, call `addGame` from their `build.zig`, and `@import("eggy")`. It publishes three modules:

- `src/core/` (`eggy`, every platform): the engine games and plugins import. `app.zig` owns SDL, the window and `Graphics`; `graphics.zig` renders through Vitellus: `Graphics` owns the device and the main window's `Surface` (a swapchain and its frames in flight, each split into `beginFrame`/`endFrame`), and `addSurface` gives other windows their own; `viewport3d.zig` draws the 3D scene in HDR, graded into its target by `scene_post.zig` (bloom, tone mapping, colour grading, FXAA) with the `PostProcess` settings of `post_process.zig` (`Environment.post`, or the active camera's own), which `Graphics.drawScene` puts across the window (the runtime) and `scene_texture.zig` renders offscreen for a panel (the editor's Scene); `plugins.zig` defines the plugin hooks and runs them; `entry.zig` provides the SDL main callbacks and fatal-error reporting both executables use, `log/` the desktop log (the level shown, set by `--log-level` or the editor's preference; a file per run under the data folder's `logs/`; and the crash report a fatal error or panic writes beside it), and `process_init.zig` the `std.process.Init` it hands `App` (`app.process_init`), since SDL's callbacks replace `main`. Shader sources live in `src/core/shaders/`.
- `src/runtime/` (`eggy_runtime`, every platform including the web): `Runtime(project)` runs a game and its plugins.
- `src/editor/` (`eggy_editor`, desktop only): `Editor(project)` runs a game with Weeoui tooling drawn over it; `workspace.zig` builds, draws and routes input for each window (the drawn title bar over the dock, and each pop-out), `workspace_tabs.zig` its tabs (whole dock layouts, any number of 3D, 2D, UI or panels dragged onto the bar, pinned ones first, one shown and the others waiting or popped out into windows of their own, or none) with `tab_bar.zig` the bar under the title bar, `tab_drag.zig` a tab dragged from it (reordered, resting on another tab to show it, its panels docked into that tab's layout), and `tab_views.zig` each tab's own Scene camera, 2D view and UI scene (each tab has its own copy of those panels, and a 3D or 2D tab of the Hierarchy, Inspector, Console, Assets and Animation around its Scene or 2D Scene, `panels.copyId`; one copy of each is live and drawn, `panels.Live`), `scene_tabs.zig` which scene each 3D tab shows (a scene dragged onto the bar opens in a new one; the others' worlds wait, unsaved edits and all), `scene_2d/` the 2D Scene panel (the world seen flat through an orthographic camera, with a grid, pan, zoom and dragging entities, and the Scene's floating toolbar with its 2D buttons; `handles.zig` the selection's box, with corners that scale it and a knob that turns it, shown by the tool picked), `menus.zig` holds the menus, `panels.zig` what each panel shows, `popout.zig` the OS window a panel pops out into, `tool_window.zig` the editor's own small windows, `terminal_view.zig` a terminal-looking output box, `file_manager.zig` File > Open in > File Manager (and Open in > IDE, through `code_editor.zig`), `devtools_window.zig` Help > DevTools, `help_menu.zig` Help's links out (documentation, issues, the log files), `asset_preview.zig` the Asset Preview panel (the file selected in Assets as itself, or in an asset tab one file of its own (`Tabs.previews`): dragged onto the tab bar, or double-clicked into a window whose closing closes the tab: images with GIFs playing, UI scenes, text, sounds in `sound_preview.zig`, a waveform to play from, and models in `model_preview.zig`, a viewer to turn, with what they are made of and their animations to play), `hit_test.zig` which element is under a point, `play_button.zig`, `pause_button.zig` and `reload_button.zig` the title bar's buttons (`play_camera_prompt.zig` is Shift+Play's choice of camera), `code_editor.zig` opening code in the chosen code editor, `scene_view/` the Scene panel (its camera, floating toolbar, orientation widget, click-to-select picking and the ImGuizmo-style gizmo, which edits `Transform` through `game_api.zig`), `window_placement.zig` the window's place carried across Reload, `build_window.zig` the Build progress window shown (with the editor frozen) while the project's editor rebuilds, `build_progress.zig` the build's progress (stage, bar, and output with its steps pinned) that it and the project loading screen both draw, `export/` File > Export (its platforms, the settings each offers and the `zig build export` arguments they become, their icons, and the progress of an export; plugins add platforms and settings through `export_platforms`, `exportUi` and `exportArgs`), and `icon.zig` the editor's icon from `resources/icon.png` (on its windows, and drawn in Help > About Eggy). `plugin_manager/` is Edit > Plugins...: the window listing installed, built-in and fetched plugins with their read-me (`plugin_manager.zig`), where a plugin's `eggy.zon` and package are (`source.zig`), reading them in the background (`fetch.zig`), and fetching the package, checking its fingerprint and saving it as a dependency (`install.zig`), and taking it back out of `build.zig.zon` when the last plugin from it is uninstalled (`package_removal.zig`), with the `eggy.zon` list they write in `project_plugins.zig`; `auto_update.zig` offers newer versions of fetched plugins when a project opens and hourly (the `update_plugins` preference), installing each only once the person agrees in `update_prompt.zig`; dropping a plugin's `eggy.zon` on the editor opens it there. `projects/` is File > New Project and Open Project: the wizard, the background job that unpacks the engine and writes the template (new projects) or reads `eggy.zon` and repairs a missing engine path (opened ones), then builds the project's editor (`job.zig`), which unpacked Eggy a project builds against, which is newest and which checkout is being developed (`engine.zig`, recorded in `engines/latest` and `engines/developer`), what the open project could move to (`upgrades.zig`: File > Upgrade Editor, and with Shift held Link Developer Eggy and Open Project with Developer Eggy), a stamp of its sources so refocusing rebuilds only after a change (`source_stamp.zig`), how far a linked Eggy codebase moved since the editor started (`eggy_update.zig`: its commits by Conventional Commit type, `!` or `BREAKING CHANGE:` marking breaking ones, and its semver version), which `src/editor/eggy_update_prompt.zig` asks about before a refocus or Reload rebuilds onto breaking changes (with the whole changelog when extreme: a major version or five breaking changes; skipping stops automatic rebuilds for the session), and the loading screen; on success it opens `<project>/zig-out/bin/<name>_editor --project <dir>` and quits. The main window's status bar shows the open project. Never add it to the web build.
- `resources/`: files the editor ships with, installed to `zig-out/resources/`. `resources/template/` is the new-project template, with placeholders `eggy_template_name`, `eggy_template_title`, the fingerprint, and the `eggy_template_engine` dependency; keep it valid Zig as written. The build packs it into `zig-out/resources/template.tar`, and Eggy's own package (build.zig.zon's `.paths`, less the submodules) into `zig-out/resources/eggy.tar`, with `src/build/tar.zig`. New projects build against `eggy.tar`, unpacked once per version into the user's data folder (`engines/<hash>`) and referenced by relative path.
- A project's `eggy.zon` (beside `build.zig.zon`) holds its settings for Eggy; `src/core/project.zig` reads it.
- Assets: `src/core/assets/` is the `eggy_assets` module (re-exported as `eggy.assets`, kept free of the engine so tools can use it): file kinds, descriptors (`<name>.eggy` beside every file and folder in `resources/`, which `src/editor/assets/descriptors.zig` keeps in step and `file_ops.zig` moves with their files), and the `.eggmodel` and `.eggtexture` formats (s2s). Models and images: the editor imports model files and decodes images through `eggy_assimp`, a shared library holding assimp and stb_image (`src/model_import/`, built by `src/build/models.zig` and `assimp.zig` from assimp's GitHub release, a lazy dependency) installed into `lib/`. A model opens into virtual children (`subassets.zig`): its Static or Skeletal geometry, its clips and its material textures, which the Assets panel saves out as PNGs (`src/editor/assets/png_writer.zig`); `addGame` packages a game's models and textures into `<prefix>/data/` as `.eggmodel`s and `.eggtexture`s, and copies every other resource there as it is, each named after its descriptor's id with `data/manifest.zon` mapping paths to ids (`src/build/resources.zig`, `src/core/assets/manifest.zig`), for the runtime (`src/runtime/packaged_assets.zig`), which starts in the scene `-Dscene` names, else `eggy.zon`'s `.default_scene` (export needs one of these), else the one the editor has open, else the first. `src/build/metadata.zig` puts `eggy.zon`'s title, version and `.metadata` into the runtime's executable (a Windows version resource, and an `.eggy_metadata` section the runtime exports); the Preferences window's Project section (`src/editor/project_settings.zig`, which File > Project Settings opens) edits them and the default scene. `Graphics.models` (`model_cache.zig`) and `Graphics.textures` (`texture_cache.zig`) hold them on the GPU, through whichever loaders the executable set.
- UI scenes: a `.ui.zon` (`src/core/assets/ui_scene.zig`, kind `.ui`) is a tree of UI nodes (panels, text in the scene's font or a font asset of its own (`.ttf`/`.otf`, kind `.font`, loaded by `cache.Images` as a companion face sharing the context's atlas), images with GIFs playing, buttons, progress bars, nested UI scenes, and plugin widgets from `ui_widgets`/`uiWidget`) with a theme over Eggy's. `src/core/ui_scenes/` shows them on entities: `UiScreen` over the game (built into the game UI before `gameUi`) and `UiBillboard` in the world (painted offscreen by `billboards.zig` into one shared texture and drawn as `world_draw` panels); `app.uiScenes()` overrides nodes by name and reports presses, also sent as `Clicked` events. `src/editor/ui_designer/` is the UI Designer, three dock panels that open together floating (`Workspace.showUiDesigner`): the preview with grid and drag (`preview.zig`), the UI Tree, which is the Hierarchy's page with `subject = .ui_nodes` (`tree.zig`), and UI Properties, which draws fields with the Inspector's `FieldEditor` from editor-side views of the format's types (`properties.zig`); its edits are History steps of the file's text.
- 2D: `src/core/sprite.zig` is the `Sprite` component (an image, or part of one, drawn flat facing +z, sorted by layer), which `mesh.gather` turns into `.quad` drawables showing their `uv_rect`, so sprites are picked, outlined and hidden like meshes. `src/core/sprite_animator.zig` is `SpriteAnimator`, which plays a run of a sprite sheet's frames (the image cut into a grid) on game time; `mesh.gather` shows its current frame, so the editor shows it too, and the Asset Preview numbers an image's frames as a sprite sheet. `src/core/tilemap.zig` is `Tilemap`: a `.tilemap.zon` (kind `.tilemap`, `src/core/assets/tilemap.zig`: the tileset's grid, the map's size and its tiles) drawn with a tileset image; both executables' model loaders build the map file into one model (a quad per tile), so a map is one drawable. `src/editor/scene_2d/tile_brush.zig` paints the selected map in the 2D panel, each stroke a History `tilemap` step.
- Sound: `src/core/audio/` is `eggy.audio`. miniaudio (a `build.zig.zon` dependency, built with stb_vorbis into a static library by `src/build/audio.zig`) decodes, mixes, buses and spatializes behind the C shim `mixer.c` (`mixer.zig` binds it; nothing translates miniaudio.h), and SDL's audio stream plays the mix (`host.zig`, made by `App`, so its callback is the host's code). `voices.zig` is `app.audio()`; `sources.zig` the `AudioSource` and `AudioListener` components and the step `App.updateWorld` runs. Voices made by the game library run its code, so `App.resetWorld` ends every voice before a reload unloads it; the editor's pause holds the mix, and the Asset Preview plays sounds.
- Dev console: `src/core/dev_console/` is `eggy.dev_console`, owned as `app.dev_console`. A line runs Eggy's commands (`builtin_commands.zig`, which reach components through `app.scene_access`, so the editor's typed steps stay in the game library), then the game's and plugins' `console_commands`/`consoleCommand` (`plugins.Set.consoleCommands`; across the hot-reload boundary, `HotGame.consoleCommands` and `game_api.console_command`), else Buzz in one REPL that lasts (`buzz_session.zig`); `run <path.buzz>` runs a file from the working directory in that REPL (`DevConsole.runScript`). `prompt.zig` is the input line with history and Tab completion (`completion.zig`); weeoui moves focus on Tab before a frame, so hosts hand Tab to `Prompt.takeTab` at the event. `overlay.zig` shows it as a bar along the bottom of the game on ` in its own colours (`palette.zig`), unless `eggy.zon`'s `.dev_console = false` (Project settings) turns it off: the runtime routes events to it first, the editor from `game_input.route` in Play, and the editor's Console panel builds the same prompt under its messages, the output logged (`log_output`). Buzz (a `build.zig.zon` dependency with pcre2 and MIR) is compiled from its sources by `src/build/buzz.zig`, never through Buzz's own build.zig, with its natives' `export`s made private so they can't stand in for libc's; on the web and Android the module is a stub (`available = false`) and only commands run. Not sandboxed.
- Scene streaming: `Scenes.stream` (`src/core/scenes/stream.zig`, stepped by `App.updateWorld`) reads a scene in the background, warms the models and images it names one a frame, then places it beside the world or in its place; `loading_screen.zig` covers the game meanwhile (scene, bar, what is loading), drawn by the runtime and the editor's Play. `src/core/particles.zig` (`app.particles`) emits camera-facing world sprites stepped on game time; `src/core/localization.zig` reads a `.zon` table of keys and text per locale.
- Editor extensions beyond panels: a plugin's `component_inspectors` draw a component's Inspector body (`inspector.zig`'s `Details.CustomUi`), `asset_importers` convert files brought into the project (`Editor.importFile`, `file_ops.saveImported`), and `scene_tools` add Scene toolbar buttons that take the pointer from the gizmo (`SceneView.usePluginTool`; a stroke is one undo step through `extensions.beginStroke`/`endStroke`). Multi-select lives in `src/editor/entities/selection.zig`; the gizmo carries the others along. `src/editor/crash_recovery.zig` keeps a copy of unsaved scene changes in `<project>/.eggy/recovery/scene.zon` (refreshed with the unsaved check, written at once when a frame or event fails, deleted on save or a deliberate discard), and the next editor sets it aside and offers it back through `recovery_prompt.zig`.
- Shaders: a project's `.slang` (kind `.shader`) does `#include "eggy"` (`src/core/shaders/eggy.slang`, the library Eggy's mesh shader builds on too); `src/core/shaders/compose.zig` inlines the library and puts the project's function into Eggy's wrapper for its role, told by the input it takes (`post_pass.slang` for `post(PostInput)`, `mesh.slang` for `surface(SurfaceInput)`). `Graphics.shaders` (`shader_cache.zig`) holds them compiled, through whichever loader the executable set: the editor's composes and compiles while running (`project_assets.zig`, through `eggy.slangc`), and `addGame` compiles each for the packaged game (`src/build/shaders.zig`, `<id>.frag` beside the copied source). A `PostProcess`'s `passes` run post shaders over the HDR scene before bloom and grading (`scene_post.zig`), and a `Material`'s `shader` gives its meshes a surface shader (`mesh_renderer.zig`, which sorts drawables by it); both make their pipelines through `shader_pipelines.zig`, remade when `ShaderCache.revision` moves.
- Project icon: `eggy.zon`'s `.icon` (an image, chosen in Project settings) is badged onto the editor's egg icon (`src/editor/icon.zig`).
- Components: a plugin lists its ECS component types in `components`; `src/core/components.zig` describes them and reads and writes their fields as ZON, and `plugins.Set.Components` collects them; a type's `category` (or else its plugin's name) is the group Add component opens it under, on a click, before anything is typed (`src/editor/entities/inspector.zig`), as an `EditorFileType`'s is in Assets > New (`src/editor/assets/creation.zig` lists Eggy's own in category order). In the editor every typed step runs in the game's library (component types and clutch's type numbering live there) behind `game_api.zig`; the editor itself walks entities and the parent tree. `src/editor/entities/` holds the Hierarchy page and the Inspector's entity view; each field's type crosses as a list of parts (`components.Part`), which `field_editor.zig` draws a control for, editing the field's ZON with `field_value.zig`. A `SceneInstance` (`src/core/scene_instance.zig`) stands for a scene file: scenes save the instance, not its entities, and `src/core/scene_instances.zig` makes them under it, in the editor's world and the runtime's, from whatever `Files` it is given. Fields changed in an instance's entities are its own: `Scene.capture` saves them on the instance (`Scene.Entity.overrides`) and `instantiate` hands them back, through `Access.instances` (`App.instanceHooks`, which the editor's `HotGame.sceneAccess` and the runtime attach); the Hierarchy lists those entities, tinted, to tune but not move.
- Distributable plugins: a plugin's folder holds an `eggy.zon` with a `.plugin` section (title, module, semver version, repository, the package's `build.zig.zon` fingerprint, `dev`) and a `README.md`; `src/core/plugin_manifest.zig` reads it, and a project's `eggy.zon` lists what it installed under `.plugins`, which `addGame` builds the game with (`src/build/game_plugins.zig`). Dev plugins (`dev`, or `GameOptions.dev_plugins`) are left out when the runtime builds with `-Ddev-plugins=false`, as `zig build export` does. `plugins/<folder>/` holds the plugins that ship inside Eggy (Git, Frame Stats, and Android, which adds File > Export's Android platform: its version and processor become `-Dtarget`, through `ExportArgs.buildFor`, and `src/build/android.zig` builds the APK for API levels `min_api` to `max_api`): `src/build/builtin_plugins.zig` publishes each as a module of Eggy and embeds their manifests and read-mes for the editor. Their `eggy.zon` names Eggy's own fingerprint and `.package = "eggy"`.
- Preferences: a plugin's `Preferences` struct is its manifest (`src/core/preferences.zig`), read with `app.preferences(T)`. Values layer defaults, the user's global folder (Eggy's data folder; the editor's own `preferences.zon` only: plugin preferences are per project) and the project's `.eggy/` (`preferences.zon` for the editor's, `plugins/<key>.zon` per plugin, and `plugins.zon`, which the editor rewrites). Keys come from `addGame` (`plugin_keys`: `game`, then each plugin module's published name), not `@typeName`, which names types after their file. `addGame` bakes `.eggy/plugins/*.zon` into the runtime's project module only, so preference edits don't rebuild the editor's game library. `src/editor/preferences/` holds the files and the Edit > Preferences window.

`build.zig`'s public `addGame` builds a game: it generates an `eggy_project` module (the game's name and plugin types) and compiles `src/runtime/main.zig` against it. The editor compiles `src/editor/main.zig` against a project module with the name only, and loads the game and its plugins from a shared library (`<name>_game`, installed beside it, rooted at `src/editor/hot_reload/library.zig`), which it swaps for a rebuilt one while running (`src/editor/hot_reload/`). Only C-callable functions cross that boundary (`game_api.zig`); Eggy's types cross as pointers, so the editor and library must be built from the same Eggy, and the editor reloads itself rather than swap when Eggy changed. This repo builds its own executables, `eggy_runtime` and `eggy_editor`, from an empty project through the same path; a game's runtime takes the game's name and its editor is `<name>_editor`.

An Eggy package follows Zig's layout: `src/main.zig` is a game (`pub const Game`, built with `addGame`) and `src/root.zig` is a plugin or library (`pub const Plugin`, published with `addPlugin`). `addGame` and `addPlugin` must request eggy with identical arguments (see `eggyDependency`) so a package's game and plugin share one engine; do not give either helper extra eggy options.

Code both executables need belongs in `eggy`; keep it free of editor-only dependencies. The game is the first plugin: keep game and plugin hooks one interface, and document any new hook in `plugins.zig` and in `docs/docs/reference/plugin-hooks.md`. Plugins are static (compiled in through `addGame`) for now.

`build.zig.zon` pins Vitellus, weeoui, humpty and clutch by git URL and commit, because Zig's package manager does not fetch submodules. `src/vitellus`, `src/humpty`, `src/weeoui` and `src/clutch` are Git submodules for local work: build against them with `--fork=src/<name>`. Commit and push changes in their own repositories, then re-pin Eggy with `zig fetch --save=<name> git+https://github.com/eggyengine/<name>#<commit>` and update the submodule pointer to the same commit. weeoui must pin the same Vitellus commit as Eggy, or `--fork=src/vitellus` fails with two Vitellus packages. Likewise humpty must pin clutch with the same package hash as Eggy (Zig identifies packages by hash, so commits that differ only outside clutch's `.paths` still match): humpty's physics runs on the world `App` owns, re-exported as `eggy.ecs`.

## README Files

Every `README.md` in this repository and its submodules is off limits to agents, with one exception: the review note every pull request adds to the repository's root `README.md` (see Pull Request Guidelines). Do not create, edit, reformat, or delete one unless a human explicitly asks for that change, and then change only what they asked for. Never update a README as a side effect of other work, even to document something you just built: put that in code comments, doc comments, or this file instead, and mention in your reply that the README may need a human's update.

When a human does ask for a README change, keep it short and clean. Write for the people who use the project. No changelogs, no implementation details, no status notes, and no repeated content.

## Documentation

`docs/` is the Docusaurus site, published to GitHub Pages by `.github/workflows/docs.yml`. Pages live in `docs/docs/`; guides go in `docs/docs/guides/`, which the sidebar shows as "Guides". Run `npm ci` then `npm run start` in `docs/` to preview, and `npm run build` to check it builds (broken links fail it). Write the guides for people making games with Eggy, not for people working on it.

## Build, Test, and Development Commands

- `git submodule update --init --recursive`: populate the submodule checkouts after cloning.
- `zig build all`: build `eggy_runtime` and `eggy_editor` into `zig-out/bin/` without running them.
- `zig build runtime` / `zig build editor`: build one executable without running it.
- `zig build run`: build and launch the editor. On the web, where there is no editor, it opens the runtime in a browser.
- `zig build run-runtime`: build and launch the runtime.
- `zig build test`: run every test. `zig build test-core`, `test-runtime` and `test-editor` run one part's tests.
- Add `--fork=src/vitellus --fork=src/weeoui --fork=src/humpty --fork=src/clutch` to any command to build against the local submodules instead of the pinned commits.
- `.github/workflows/nightly.yml` builds `zig build all -Doptimize=safe` for Linux, Windows and macOS each night the default branch changed, kept as workflow artifacts (not releases).
- `zig build update-submodules`: fetch the latest configured submodule branches. Review and commit changed pointers before sharing them.
- `scripts/get-started.sh`: `curl -fsSL https://raw.githubusercontent.com/eggyengine/eggy/main/scripts/get-started.sh | bash` asks for a title, package name and directory, then writes `resources/template` and fetches Eggy. Prompts are read from the terminal, so the pipe does not swallow them. If Zig 0.17 is missing it asks before installing zvm and Zig. It refuses to start unless the other tools it runs are present, then checks Zig's standard library, every template file, and runs `zig build --fetch` for the project's required packages, then offers to compile and open the editor (`zig build run`). On Windows, `irm https://raw.githubusercontent.com/eggyengine/eggy/main/scripts/get-started.ps1 | iex` does the same from PowerShell.

## Coding Style & Naming Conventions

Run `zig fmt` on changed Zig files. Follow the existing four-space indentation, `PascalCase` types such as `Graphics`, and `camelCase` functions such as `syncSize`. Keep platform-specific code behind target checks. Vitellus core accepts generic window handles; Eggy wires in the SDL adapter in `build.zig`, so do not add an unconditional SDL dependency to Vitellus.

## Readable Code

Write code that a newcomer can follow without opening every helper. These rules apply to every change, including small ones.

**Make the smallest complete change.**

- Solve the whole task with the least new code. Reuse what the codebase, the standard library, or an existing dependency already provides before writing anything new.
- Do not add options, abstractions, wrappers, or "for later" code that the task does not need. Deleting code beats adding it.
- Finish everything the change touches: callers, tests, docs, and build files.
- Mark a known limitation where it lives: `// ponytail: <the limit>, <when to upgrade>`.

**Organize by feature.**

- Put code where its feature name says it is. Split a file when it mixes separate jobs, not when it reaches a line count. A long file with one concept is fine.
- No god files. A file owns one feature, and its `//!` comment says which in one sentence; if that sentence needs "and", split the file. Do not grow `app.zig`, `graphics.zig`, `editor.zig`, `runtime.zig`, `root.zig` or `build.zig` into catch-alls: they wire features together and delegate, and new behaviour goes in its own file beside them (as `scene_texture.zig` and `workspace.zig` do).
- Keep `root.zig` files to the module's doc comment, re-exports, and the `test` block that pulls in each file's tests. Logic lives in the feature files they export.
- When a feature grows several files, give it a directory named after it with a file of the same name as its entry point, for example `src/editor/panels/panels.zig`. Callers import that entry point, not the files behind it.
- Dependencies point one way: `editor` and `runtime` depend on `core`, never the reverse, and feature files in one module do not import each other in cycles. Pass what a file needs as parameters instead of reaching into another feature's internals.
- Keep each file's public surface small. Mark helpers private unless another file needs them, and expose the feature through a few types and functions with `///` contracts.
- Add a layer or helper only when it hides real detail or owns an invariant. Leave short, cohesive sequences inline.

**Name and type for meaning.**

- Name things after what they mean in the domain and what they do, including side effects. Avoid vague names such as `process` or `data`.
- Put units in names when they are ambiguous, for example `time_ms` or `extent_px`.
- Prefer enums and tagged unions over boolean mode flags and magic numbers.
- Validate input at boundaries and pass the validated values inward.

**Keep control flow straight.**

- Present a workflow's steps in execution order. Use guard clauses so the main path stays visible.
- Keep side effects, ordering constraints, and `errdefer` cleanup visible in the function that owns them.
- Do not swallow errors or turn a failure into success by accident.

### Block comments

Give each meaningful block of code a single short comment that states its purpose: why it is there, or what it achieves. Put it above the block. It is a heading, not a narration.

```zig
pub fn frame(self: *Graphics) !void {
    // Reuse this slot only once the GPU has finished the frame that last used it.
    const slot = &self.slots[self.slot];
    _ = try self.gpu_done.wait(slot.frame, null);
    try slot.commands.reset();

    // Record the scene into the acquired swapchain image.
    const acquired = try self.swapchain.acquireNextImage(slot.acquired);
    const cmd = try vit.CommandBuffer.init(slot.commands, .{});
    try self.preview.draw(cmd, acquired.view, ...);
    try cmd.finish();

    // Submit, then present once rendering signals `render_done`.
    try self.queue.submit(...);
    _ = try self.swapchain.present(&.{render_done});
}
```

- Keep each comment to one line where possible. Explain intent, invariants, and surprising ordering, not syntax.
- Do not comment every line or restate the code. If a block needs a long explanation, improve the names or structure first.
- Give non-trivial types and public functions a `///` doc comment that describes their role and contract: preconditions, side effects, and failure behaviour. Use `//!` at the top of a file to state the module's purpose.
- When behaviour changes, update its comments in the same commit.

## Testing Guidelines

Place small Zig `test "behavior"` blocks beside the code they exercise. Name each test after the behavior it checks, and keep its decisive inputs and expected outcomes visible in the test. Run `zig build test` for code changes and `zig build run` and `zig build run-runtime` when changing windowing or graphics. For visual changes, check the desktop window when available. There is no repository-wide coverage threshold.

## Commit Guidelines

Use [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): summary`.

- **type**: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`, or `release`.
- **scope**: the module or area touched, such as `core`, `runtime`, `editor`, `graphics`, `shaders`, `build`, `vitellus`, `weeoui`, or `humpty`. Omit it only when the change is genuinely repo-wide.
- **summary**: imperative, lower case, no trailing period, at most about 72 characters.
- Mark breaking changes with `!` after the scope, and explain the break in the body under `BREAKING CHANGE:`.
- Use the body for the reasoning behind the change, not a list of files.

```text
feat(graphics): resize the depth buffer with the swapchain
fix(game): stop the frame cap from delaying web builds
refactor(weeoui): split measure-and-place out of layout.zig
build(vitellus): replace dynlib.zig with better-dynlib
release(eggy): v0.2.0
```

Keep each commit focused on one change. When you bump a submodule pointer, name it in a commit of its own, for example `build(weeoui): bump to 1a2b3c4`.

## Pull Request Guidelines

Pull requests should describe the behavior changed, list the commands run, link an issue when applicable, and include a screenshot or recording for visible rendering changes. Call out submodule revision changes explicitly.

**Agents must write this note into the repository's root `README.md` file, at the very top, as a commit on the pull request's branch, for every pull request they open.** It goes in the file itself, so it shows in the pull request's diff; putting it only in the pull request's description does not count:

```markdown
> [!NOTE]
> By removing this, you prove that the code has been reviewed by human.
```

Agents must never remove, reword, or hide this note, and never open a pull request without it in `README.md`. Only a human reviewer removes it from `README.md`, once they have reviewed the code.
